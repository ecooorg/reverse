**CREA 0.2 — Deep Process & Performance Intelligence**.

 Не начинать сразу с Ghidra и не пытаться одновременно реализовать все внешние анализаторы. Сначала я бы существенно усилил способность CREA самостоятельно исследовать работающие программы, обнаруживать реальные проблемы производительности и собирать доказательства.

Причина простая: главная задача CREA — не просто распознавать бинарники, а помогать ИИ-агенту находить причины избыточного потребления ресурсов и объективно проверять результаты оптимизации.

В твоём ТЗ это соответствует приоритетам Performance Profiler, Process Manager, Evidence Engine и Benchmark Engine.

# CREA 0.2 — Deep Process & Performance Intelligence

Я бы включил в патч семь крупных направлений.

## 1. Advanced Process Inspector

Сделать полноценный сбор информации о работающих процессах.

### Что реализовать

- Получение PID, PPID и дерева процессов.
- Определение исполняемого файла.
- Определение аргументов запуска.
- Определение времени работы процесса.
- Количество потоков.
- Использование RAM.
- Виртуальная память.
- CPU utilization.
- Накопленное CPU time.
- Дисковый I/O.
- Открытые файловые дескрипторы, где доступны.
- Определение дочерних процессов.
- Обнаружение процессов, потребляющих непропорционально много ресурсов.

**Особенно важно:** реализовать наблюдение за процессом в течение заданного интервала, а не просто получать моментальный снимок.

Например:

```text
Target Process: example

PID: 12450
CPU:
  Average: 34.2%
  Peak: 87.5%

Memory:
  Average RSS: 428 MB
  Peak RSS: 612 MB

Threads: 18

Disk I/O:
  Read: 128 MB
  Write: 42 MB

Observation:
  Duration: 60 seconds
  Samples: 60
```

Это позволит агенту видеть не только текущее состояние, но и динамику потребления ресурсов.

## 2. Time-Series Performance Profiler

Это, пожалуй, самая важная часть патча.

Сейчас недостаточно просто получить CPU и RAM. Нужно создать механизм временных измерений.

### Реализовать

- Сбор показателей с заданной частотой.
- CPU utilization по интервалам.
- RSS и VMS.
- Пиковое потребление RAM.
- Изменение потребления памяти.
- CPU time.
- Read/Write I/O.
- Количество потоков.
- Обнаружение резких скачков нагрузки.
- Обнаружение продолжительной высокой нагрузки.
- Выявление процессов с постоянно растущей памятью.

Предусмотреть режимы:

| Режим | Назначение |
|---|---|
| Snapshot | Однократное измерение |
| Monitor | Непрерывное наблюдение |
| Diagnostic | Расширенный сбор показателей |
| Compare | Сравнение двух периодов |

Результаты должны сохраняться в структурированном формате.

Например, агент должен иметь возможность выяснить:

- RAM постоянно растёт?
- CPU периодически достигает 100%?
- Процесс простаивает, но продолжает потреблять ресурсы?
- После определённого события начинается увеличение нагрузки?
- Какой дочерний процесс создаёт основную нагрузку?

### Важное ограничение

Не называть это обнаружением горячих функций.

Без Frida, perf, eBPF или другого соответствующего профилировщика мы можем достоверно определить ресурсоёмкие процессы, но не конкретные функции внутри них.

## 3. Advanced Benchmark Engine

Я бы серьёзно расширил существующий Benchmark Engine.

Сейчас его задача — сравнивать выполнение программ до и после изменений. Следующим этапом нужно сделать измерения более научно обоснованными.

### Добавить

1. Несколько повторных запусков.
2. Warm-up перед измерениями.
3. Разделение cold и warm runs.
4. Среднее время выполнения.
5. Медиану.
6. Минимум и максимум.
7. P95.
8. Стандартное отклонение.
9. MAD — Median Absolute Deviation.
10. Определение выбросов.
11. Сравнение CPU time.
12. Сравнение максимальной RAM.
13. Сравнение размера бинарника.
14. Фиксацию конфигурации системы.

Пример:

```text
BENCHMARK COMPARISON

Metric              Baseline      Optimized

Execution Time      2.840 s       1.920 s
CPU Time            2.510 s       1.640 s
Peak RAM            512 MB        384 MB
Binary Size         42.8 MB       38.2 MB

Performance:
  Execution: -32.4%
  CPU Time:  -34.7%
  RAM:       -25.0%
  Size:      -10.7%

Statistical Confidence:
  Repetitions: 20
  Median: Available
  MAD: Available

Result:
  IMPROVEMENT DETECTED
```

При этом нельзя автоматически объявлять статистическую значимость только по снижению среднего времени. Нужно учитывать разброс измерений и условия эксперимента.

## 4. Advanced Evidence Engine

Это второй по важности архитектурный компонент.

Я бы сделал Evidence Engine центральной системой хранения технических фактов.

Каждое исследование должно формировать доказательства:

- Process Evidence.
- Memory Evidence.
- CPU Evidence.
- I/O Evidence.
- Binary Evidence.
- Benchmark Evidence.
- Validation Evidence.

У каждого доказательства должны быть:

| Поле | Назначение |
|---|---|
| evidence_id | Уникальный идентификатор |
| target_id | Исследуемая программа |
| type | Тип доказательства |
| source | Источник информации |
| timestamp | Время получения |
| measurement | Измеренные данные |
| confidence | Уровень достоверности |
| limitations | Ограничения |
| hash | Контрольная сумма |

Особенно важно реализовать связь:

```text
Research Session
    |
    +-- Target
    |
    +-- Process Observations
    |
    +-- Performance Profile
    |
    +-- Baseline
    |
    +-- Optimization
    |
    +-- New Benchmark
    |
    +-- Comparison
    |
    +-- Validation
    |
    +-- Final Evidence Report
```

Это позволит ИИ получать не разрозненные JSON-ответы, а полную историю исследования.

## 5. Benchmark Environment Fingerprinting

Это функция, которую я настоятельно рекомендую добавить уже сейчас.

При сравнении двух версий программы важно знать, в одинаковых ли условиях проводились измерения.

Фиксировать:

- ОС и версию.
- Архитектуру процессора.
- Количество CPU cores.
- Общую RAM.
- Версию Node.js.
- Версию CREA.
- Версию исследуемого приложения.
- Аргументы запуска.
- Переменные окружения, исключая секреты.
- Время проведения исследования.
- Параметры benchmark.

Если оборудование или конфигурация существенно отличаются, CREA должен предупреждать об ограниченной сопоставимости результатов.

## 6. Process Safety & Resource Control

Вместе с расширением профилирования необходимо усилить безопасность.

Реализовать:

- Проверку существования PID.
- Проверку идентичности процесса перед операцией.
- Защиту от повторного использования PID.
- Timeout для запуска исследуемых процессов.
- Ограничение размера stdout/stderr.
- Контроль запуска дочерних процессов.
- Корректное завершение собственных тестовых процессов.
- Отмену исследования.
- Безопасное удаление временных файлов.

Отдельно предусмотреть режимы:

```text
READ_ONLY
OBSERVE
CONTROLLED_EXECUTION
```

По умолчанию — READ_ONLY.

Важно: контроль CPU и RAM не должен изображаться как полноценная системная изоляция. Для настоящих жёстких ограничений потребуются отдельные механизмы ОС, например cgroups на Linux.

# Мой окончательный вердикт

Я бы не делал CREA 0.2 просто расширением количества анализаторов.

Я бы превратил его в **полноценную систему исследования производительности программного обеспечения**.

Причём с тремя главными преимуществами:

- **Deep Observation:** CREA знает, что происходит внутри исследуемой системы на уровне доступных системных показателей.
- **Scientific Benchmarking:** CREA умеет объективно измерять эффективность изменений.
- **Verifiable Evidence:** CREA способен доказать, откуда получены данные и на чём основаны выводы.

И ещё один важный момент: я рекомендую сделать Linux первым полноценно поддерживаемым профилируемым окружением, но сразу заложить интерфейсы для Windows и macOS.

**Именно такой CREA станет действительно полезным инструментом для автономного ИИ-агента оптимизации ПО, а не просто MCP-обёрткой над набором системных команд.**
